# Configure networking

**Purpose:** For openCenter operators, shows how to set networking values in an openCenter cluster configuration.

Networking values are part of the v2 configuration. Keep the YAML structure
generated by `cluster init`; this page lists only fields
whose names are used by validators and fixtures.

## Choose one network plugin

The readiness validator rejects conflicting managed network plugins. A common
structural form is:

```yaml
opencenter:
  cluster:
    kubernetes:
      network_plugin:
        calico:
          enabled: true
```

Kind has a separate rule: when its default CNI is active, a managed plugin must
not also be enabled. Use `--kind-disable-default-cni` at initialization when
openCenter should manage the CNI.

When openCenter manages Calico on Kind, the bootstrap applies the Calico operator
CRDs with `kubectl apply --server-side` and then installs the Helm chart with
`--skip-crds --force-conflicts`. The Helm install does not reapply the chart CRDs,
so it does not conflict with the `kubectl` field manager. This matches the Calico
install on OpenStack.

## Configure CIDRs and VRRP

The v2 fields used by the validation fixtures include `subnet_pods`,
`subnet_services`, and infrastructure `networking.subnet_nodes`. Keep CIDRs
non-overlapping. When `use_octavia: false` and `vrrp_enabled: true`,
`vrrp_ip` is required:

```yaml
networking:
  use_octavia: false
  vrrp_enabled: true
  vrrp_ip: 10.0.0.10
```

The exact parent mapping depends on the generated v2 file; edit the existing
`networking` block rather than copying an unrelated legacy layout.

## Validate and render

```bash
opencenter cluster validate ORG/CLUSTER
opencenter cluster generate ORG/CLUSTER
```

Use `cluster validate --manifests` after generation when generated manifests
need checking. Provider connectivity is a separate `--validation online` mode.

## Evidence and ambiguity

The repository proves validation rules and plugin/provider branches, but does
not prove a universal default CIDR, load-balancer outcome, DNS outcome, or
network reachability. Those depend on the loaded configuration and target
provider.

- Network validation: `internal/config/v2/readiness.go`
- Network fixture: `tests/features/validation.feature`
- VRRP workflow: `tests/features/workflow.feature`
- Init flag: `cmd/cluster_init.go`
